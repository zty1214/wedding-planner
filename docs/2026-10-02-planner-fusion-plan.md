## 1. 目标与决策背景

以 **wedding-planner 为唯一主仓库**继续迭代，保留其现有完整产品与工作流，将数据平台统一到 **CloudBase**，有选择地迁入 wedding_project 的排座规则、协作机制和验证能力。

- **目标仓库 Planner**：`/Users/baojie/dev/wedding-planner`。后续生产实现、测试、部署配置和维护均在这里完成。
- **来源仓库 Seating**：`/Users/baojie/Downloads/同步空间/家人/zty/wedding_project`。提供可复用代码与测试参考；完成必要能力吸收和数据切换后归档，不长期并行开发。
- **数据库**：从 Planner 的 Supabase 迁移到 CloudBase。来源仓库现有 CloudBase 数据按核对结果补充到目标项目，不直接覆盖旧库。
- **交互**：已选择方案 A，即延续 Planner 现有顶部四入口、桌面排座三栏和浅色风格；首期不重新设计产品外壳。

首要成功标准：一直使用 Planner 的人，进入新产品后仍能找到原来的四个入口、名单、分组、房间、晚次、笔记和导出；日常任务不增加明显步骤，不要求重新录入真实数据。

首期目标是功能不减少、数据不丢、保存可靠、操作连续。优先改数据与业务层；只调整必要的保存反馈、状态表达和移动端可用性。不把全面视觉改版、画布替换或复杂账号体系绑定为首次数据库切换的前提，不长期维护双库双向同步。CloudBase 数据迁移与前端托管迁移可以分开实施；首期只在确有需要时同步换托管，避免额外改变入口。

### 1.2 为什么选 Planner 作为基础

Planner 已有宾客、排座、住宿、笔记、导出和项目导航，且实际使用者长期使用。以它为基础可以保留页面和操作流程，将改造集中在共同数据模型、写入与同步机制，减少功能搬迁和用户学习成本。

Seating 的优势是排座规则独立、修订号检查、条件更新、冲突处理和测试。这些模块值得迁入，但不要求产品迁入 Seating 仓库。选择 CloudBase 与选择主仓库是两个独立决定：采用 CloudBase 不意味着必须使用 Seating 的页面结构。

两边目前都主要是浏览器直连云数据库，并非已有两套完整独立后端。融合需要建立统一业务写入入口，不能只替换 SDK。CloudBase 是已选定的目标基础设施，可以复用已有部署经验；实际国内网络表现仍需验证，不预先保证优于 Supabase。

### 1.3 本次发现、必须纳入融合的问题

- Planner 的 `status` 混合排座与出席；移出桌子会设成 `unassigned`，不能从现有记录恢复已经丢失的历史确认状态。
- Planner 通过 URL 选择项目读取数据，宾客/房间写入却取 store 中的 `projectId`；未发现同步对齐动作。迁移前需核对相关项目的记录来源，不能只按页面当前项目推断归属。
- Planner 的“已同步”只由配置和项目 ID 推导，并非保存回执；部分写入错误只记控制台或未处理。
- 标题、舞台位置、自定义分组、我生成的分享链接保存在本地 store，未看到云端同步；同一 localStorage 键保存全局状态，不能假定各项目都有独立完整的本地快照。
- 笔记当前 UI 主要提供新增/删除；store 虽有 `updateNote`，同步只推送新增/删除。不能据此断言用户当前编辑功能已在线失效，但融合后的编辑功能必须有完整写入路径。
- Planner 仓库 SQL 的 RLS 策略为 `allow all`；Seating 规则也不构成成员级授权。云端实际配置待查；新项目必须验证跨项目隔离。
- Seating 当前最多 20 桌、200 位宾客，备注 200 字等校验可能拒绝 Planner 数据。预检后明确调整，不静默截断或删记录。

## 2. 保持 Planner 使用连续性

### 2.1 首个可切换版本必须具备的能力

| 原有任务 | 融合后的承诺 | 验收方法 |
| --- | --- | --- |
| 四个常用入口 | 保留“宾客名单 / 座位安排 / 住宿安排 / 备婚笔记”的名称与顺序，默认进入排座 | 用户不看说明完成四页切换 |
| 添加宾客、分组筛选 | 原标签原样保留，仍可快速输入姓名、分组、电话；新增所属方不强迫每次填写 | 与 Planner 同一任务逐步对照，无额外必填项 |
| 选桌、添人、改桌名、确认出席 | 电脑保留左侧工具、中间画布、右侧详情；8/10/12 人桌入口保留 | 使用相同桌位样本完成任务，姓名与座位可辨认 |
| 删除桌子 | Planner 原行为会解除宾客排座；融合版提供明确“移出宾客并删桌”确认，单次原子完成 | 不因 Seating 原有非空桌保护而让原任务无法完成 |
| 房间与晚次 | 保留大床房/标间、房号、添加入住人、手动点选晚次、按日期统计 | 分房不自动替用户选晚次；移出房间清空晚次 |
| 房间容量 | 保留现有超员提醒，不未经讨论改成禁止录入；按晚统计占用 | 不同晚住不同人不被误认成同晚超员 |
| 住宿统计 | 保留按房按晚计数；“已入住”改为“已安排住宿”；待办按独立住宿需求分栏 | 不把房间分配误当实际入住确认；待安排房间为明确需要且未分房；需求待确认、已分房但晚次待定单列，不需要者不计入待办 |
| 宾客 Excel | 保留原 7 列名称与顺序；显式 side 优先，unset 才按旧分组回退；覆盖“不出席” | 对照原导出，数据完整；电话按文本保留 |
| 住宿 Excel | 保留“住宿明细”和“每晚用房”两张表、日期矩阵和汇总 | 按房、按晚人数和文件列结构对账 |
| 图文笔记 | 保留酒店/婚庆/试妆/其他分类、标题可空、正文、图片顺序与时间 | 原笔记逐项可见，图片不丢失 |
| 分享与独立项目 | 保留邀请当前项目、新建独立项目和“我的项目”记录的可发现性 | 两个项目互不串数据，新浏览器打开链接可使用 |
| 刷新与协作 | 区分本机草稿与云端已同步；本机草稿可恢复，失败可重试 | 同页重连自动同步无冲突修改，重开页面须确认恢复；已同步内容跨设备可见 |
| 住宿需求 | 待确认/需要/不需要，与出席分开；不增加新增宾客必填项 | 已分房改为不需要时，确认后原子清空房间和晚次；取消则不变 |
| 历史与日历 | 回收站、手动命名版本、每日快照、活动热力图 | 多次拖动不生成多份历史；点日期看汇总和快照，恢复不覆盖后续安排 |
| 管理入口 | 私有管理链接与发给家人的协作链接分开 | 协作链接无法整项目恢复或换链接；管理凭证不泄漏到普通分享 |

一条宾客记录代表一个具体的人。“小明”“小明 2”保留为不同人，不能去掉数字合并；不引入家庭人数或批量占座。外部酒店/婚庆只接收表格或图片，不进入项目。

出席与排座分开后，移出桌子保留“确认出席”，这是明确的行为修正；标为不出席会释放座位，但不擅自取消住宿。取消住宿由独立操作完成。页面同时显示“未排座/第 N 桌”和“待确认/已确认/不出席”，避免混淆。

### 2.2 链接与切换体验

优先保留 Planner 的 `/p/<projectId>/guests|seating|stay|notes` 路由语义和现有分享入口；根路径的默认项目行为也需继续可用。能保留现有域名则优先保留，不把换网址与换数据库捆绑。若静态托管一并迁到 CloudBase，部署时验证这些深层路由直达和刷新均可用。

项目定位与访问凭证分开。旧 Planner 的 8 位项目 ID 可以作为受控映射使用，不能单独赋予新系统编辑权；保留老路径不等于无条件保留旧授权。已有使用者在切换前获得有效新协作链接或等效访问会话，不能首次打开时只遇到无法继续的权限错误。

Seating 原 `#/w/<id>` 链接只作为旧入口兼容事项：原站按已核对项目映射提示或跳转至 Planner，对应访问仍需验证。不把 Seating 的 hash 路由改成 Planner 的主路由。旧域名和部署权限待核实，不能承诺所有旧链接自动无感接入。

熟悉度验收：由一直使用 Planner 的对象，在测试副本中独立完成“加宾客→排桌→确认→分房→选两晚→导出住宿表→写笔记”。记录找不到入口、额外步骤和术语疑惑；关键任务均通过后才允许正式切换。

## 3. 融合后的工程结构

### 3.1 一套业务、一个写入口

```text
电脑布局 / 手机布局
        ↓
宾客、排座、住宿、笔记的共享控制逻辑
        ↓
Repository：订阅数据 / 执行明确业务命令 / 返回保存结果
        ↓
CloudBase 云函数：项目权限 → 参数校验 → 业务规则 → 原子提交
        ↓
CloudBase 文档数据库 + 图片对象存储
```

在 Planner 中新增领域模块与 Repository，按需要迁入 Seating 的纯函数、命令与测试。Planner 现有页面和 Zustand store 保留；store 可继续承载页面选择和经 Repository 获取的业务快照，但 action 必须通过统一命令保存，不能保留第二套直写或 diff 推送。

过渡时用薄的页面数据适配保留 `label/seats/group` 等现有字段与 action 名称，避免所有页面同时改写。适配层只转换数据和调用命令，不重新实现规则。每个试用项目一次只启用一个数据源；不在同一项目中一部分页面写 Supabase、另一部分写 CloudBase。

共享领域代码由前端与云函数构建共同引用，不复制出两份。前端可用它做即时反馈；服务器必须独立验证后再保存，客户端计算结果不具有最终写入权。

### 3.2 数据模型与首版存储建议（P1 验证后确定）

| 存储单元 | 内容 | 决策原因 |
| --- | --- | --- |
| `weddings_v2`，每项目一份当前生效的核心文档 | 标题、场地、画布、宾客、桌子、分组、房间、可选晚次、版本 | 排座交换、删除房间、删除晚次等跨对象动作可在一个原子提交中完成，复用现有快照思路 |
| `wedding_notes_v2`，每笔记一文档 | 项目 ID、分类、标题、正文、图片引用、创建/修改时间、revision | 笔记按需加载，避免每次排座传输全部笔记 |
| CloudBase 云存储 | 图片原文件，以项目隔离路径组织 | 不把 base64 图片写入核心快照 |
| 项目访问记录与命令回执 | 协作/管理凭证摘要与版本、受限会话、幂等操作回执 | 与业务数据分离，客户端不可修改权限或伪造回执 |
| 迁移记录 | 批次、来源映射、源哈希、校验结果 | 可重跑、可核对、可回滚，不是长期业务同步机制 |
| 回收站、版本快照、日活动汇总 | 按项目隔离的删除恢复材料、手动/每日/安全快照及日期汇总 | 与当前核心文档分开，按需分页读取；图片保留引用，不逐版本复制文件 |

这是复用 Seating 快照机制的首选候选方案，并非不可调整的实施约束。先测真实核心文档字节数、宾客/房间数、峰值写入和订阅流量；核对当前 CloudBase 环境模式及官方限制。如果超出允许大小或并发体验不达标，才拆住宿数据，并验证相应事务，不能盲目扩大单文档。

在 Planner 中建立融合模型 v2：保留 Planner 已有 `roomId`、`stayDates`、房间、笔记、自定义分组和桌子 `rotation`；吸收 Seating 独立出席状态、修订号与排座约束。将原混合 `status` 拆为独立 `attendance` 与由桌位引用推导的排座状态；页面可用展示适配维持熟悉措辞，不能让旧 `status` 成为第二份可写事实。

保留原分组完整文本作为显示标签，`side` 允许 unset，不强迫拆成新郎/新娘两层。内部字段可按复用需要规范化，但 Planner 页面不必全面重命名。无需第一版建立独立住宿订单或多酒店管理模型。

### 3.3 写入与并发约定

- 所有写入携带同一个明确的项目上下文。项目切换取消旧订阅；旧项目待写队列不得重定向到新项目。
- 复用 `guest.assign/swap/reorder` 等命令；增加房间、晚次、项目配置和笔记命令。批量释放座位并删桌、删房间并清空入住关联、删晚次并更新受影响宾客均为原子动作。
- 命令携带操作 ID 与受影响对象的预期 revision。服务器读取当前数据、验证归属与约束、计算下一版、原子提交。冲突返回可理解的提示，不静默覆盖他人的最新修改。
- 操作回执与变更放在同一事务内；同一操作 ID 重试返回原结果，同 ID 不同内容拒绝。未取到回执的超时不能直接认定失败并生成新 ID 重发。
- 仅在收到服务端成功回执后显示“已同步到云端”；本地草稿持久保存后显示“草稿已保存在本机，尚未同步”。断网时保留草稿，刷新/重新打开后能恢复；同页重连自动提交无冲突修改，重开页面先确认恢复，见第 9.4 节。
- 迁入 Seating 的可撤销命令设计；排座撤销按钮可后续接入，不阻塞 Planner 原功能的数据库切换。若接入，撤销必须验证当前 revision，不能覆盖别人后续编辑。各模块删除动作保留必要确认；首期采用回收站、手动版本、每日快照和筹备日历，不建立逐操作完整历史，具体见第 11 节。
- 订阅仅接收有权限的项目数据，并保留受权限约束的轮询兜底。旧快照不得覆盖新版本，远端变化不再次作为本地写入回传。

CloudBase 官方文档提供事务与权限能力，但需在实际环境/SDK 下验证。事务内只用支持的文档读写，不能把目前浏览器的 `where(...).update(...)` 原样搬进事务。相关依据：[事务操作](https://docs.cloudbase.net/database/transaction)、[云函数安全规则](https://docs.cloudbase.net/cloud-function/security-rules)。

### 3.4 最小项目隔离与图片访问

使用协作链接与独立私有管理链接，无注册账号或成员列表。服务器验证凭证所属项目与权限范围，浏览器不得直接写业务、权限、回执或历史数据。若使用匿名登录，它只提供底层会话，不能代替项目访问凭证。详细授权及链接轮换见第 9.5 节。

图片上传、查看和删除同样按项目授权；通过已验证的受控上传/下载方式实现，不以公开永久 URL 代替权限。上传失败不能显示笔记图片已保存；可先上传后提交笔记，未被引用的文件延迟清理，不在事务内执行外部上传。参考：[数据库规则](https://docs.cloudbase.net/database/security-rules)、[存储规则](https://docs.cloudbase.net/storage/security-rules)。

### 3.5 渐进落地和版本兼容

先在 Planner 的独立开发分支和 CloudBase 测试项目验证 v2，现有生产 Planner 继续用 Supabase。分别实现 Planner 原始数据→v2、Seating v1→v2 的转换；两者字段含义不同，不能共用未经区分的导入器。旧客户端不能写新集合，以免整体保存时丢字段。

CloudBase 开发/测试入口使用明确环境配置，不对生产用户按页面随机切换后端。试用副本不与生产双写。最终切换后刷新或版本提示引导旧页面加载新版本，后端同时禁止旧写入。

## 4. 数据迁移与核对

### 4.1 数据来源和优先级

暂定 Planner 为宾客基础信息、住宿和笔记的主来源，Seating 为候选补充来源。这个默认值不能自动裁决同一个人的状态或座位冲突，正式导入前由两位使用者确认。

收集：Supabase 五张表的完整分页原始导出、CloudBase 原始快照、实际常用浏览器的本地状态、图片文件或可用引用。保留来源项目、记录 ID、导出时间和源文件哈希。开发仓库、预览和普通日志只放虚构数据或汇总；真实数据备份放受控目录，不提交 Git。

先核对云端 schema 与仓库 SQL 是否一致；本地快照与云端不一致逐项列出，不一律采用云端。尤其在已发现的项目上下文风险下，导出范围应覆盖明确属于这场婚礼的相关项目，而不是按当前 URL 猜一张表的完整性。

### 4.2 映射和冲突规则

| 字段/对象 | 转换规则 |
| --- | --- |
| ID | 来源系统 + 来源项目 + 实体类型 + 旧 ID 组成稳定映射；无碰撞可保留原 UUID；冲突产生新 ID 并重写所有引用 |
| 姓名、电话、备注 | 原文保留，电话按字符串；不随意去前导零、截断、替换全角字符 |
| 分组 | 原显示标签完整保留；所属方只给推断建议，含混项保留 unset；自定义选项从本地和数据中一并补齐 |
| 出席 | Planner 来源：`confirmed→confirmed`；`assigned/unassigned→pending`；排座由引用字段决定；历史已丢失的确认不推断恢复 |
| 桌位 | 保留 Planner 的 label、seats、rotation 与 table/seat 关联；如内部模型采用 name/capacity，仅在适配层转换；两边 seatIndex 均从 0 开始 |
| 房间与日期 | 类型、房号、备注、roomId、晚次完整迁移；有房记录的住宿需求设为 needed，无房记录设为 pending，不猜测不需要；按 ISO 日期字符串保存，不做时区换日；不自动给无晚次宾客补日期 |
| 配置 | 标题、舞台位置、分组来自具体浏览器的已核对快照；入口缺失时采用可调整默认，不伪造原数据 |
| 笔记 | 标题可空；保留分类、正文、图片顺序、原创建/更新时间；base64 转文件，外链按可访问性与迁移必要性逐个核对 |
| 时间与修订 | 旧时间保留用于来源追溯；v2 revision 独立初始化，不把旧时间戳解释成新系统并发版本 |
| “我的项目” | 属于个人快捷入口，单独迁移至原使用者；不把朋友项目自动并入本场婚礼或分享给全体家人 |

重复识别只生成候选：姓名相同、电话相同均不足以自动合并，家庭可能共用电话。无法确认时保留两条并标记待核对。每条源记录都必须有目标 ID 或明确的人工处置，不能在去重过程中消失。

冲突报告至少包含：同人不同桌位/出席、重复占座、失效桌/房引用、超容量、无房间却有晚次、日期未在项目选项中、超字段限制、图片失败、未归属本地配置。原始信息留在备份与映射中；修复必须记录决定，不能为了通过校验直接移除。

首期保留 Konva，因此 Planner 原画布坐标、相对位置、舞台与座位展示应原样保留。只有纳入 Seating 的桌位数据时，才需要对其坐标、旋转、座位起点与顺逆时针做显式转换和截图对照。不能因为来源 SVG 的模型不同而重排 Planner 当前宴会厅。

### 4.3 执行顺序

1. **只读盘点与备份**：记录数量、大小、图片数、来源、字段异常；确认主来源和待裁决项。
2. **离线 dry-run**：生成规范化数据、稳定 ID 映射、差异报告，不连接写入目标。
3. **试迁移**：导入全新 staging 项目；整个批次未校验完成前不对普通用户可见。重复运行使用同一批次和映射，不重复创建；禁止覆盖已有人工修改的目标。
4. **逐项对账**：源记录覆盖率 100%；目标实体数考虑已批准合并后相符；电话/备注/状态按映射一致；桌位唯一、引用有效；按晚住宿统计一致；图片数量和内容校验，丢失项必须修复或明确认可。
5. **用户试用**：在副本完成第 2 节任务清单，确认流程和视觉；生产 Planner 继续使用，不双写测试项目。
6. **正式切换**：约定短暂停写窗口，阻止旧端继续写入，重新完整导出。由于 Planner 部分表没有可靠更新时间，不以 `updated_at` 作为唯一增量依据；优先从最终完整快照重建新的正式目标，包含删除记录的正确结果。
7. **开放融合版本**：回读校验通过后将 Planner 正式版本切到 CloudBase，尽量保留原入口；需要变化的链接提前通知。Supabase 旧部署与 Seating 旧站均停止生产写入，旧数据库保留只读备份。

旧站只换前端按钮不足以停写：已打开的旧标签页仍可能写数据库。正式窗口须在权限/后端层拒绝旧写入并验证。方案实施完成后，再对具体切换批次、停写时间和目标申请最终确认。

### 4.4 回滚

- 新站尚无正式新增写入：恢复旧站写权限和入口，保留失败批次排查。
- 新站已有正式写入：先停写并导出新数据，整理切换后的变更；经核对反向补入旧格式后才恢复旧系统。旧格式不能表达的新字段必须保留独立备份并明确处理。
- 未能保证反向补齐时，先只读维护并修复新站，不能直接回退而丢掉新修改。
- 稳定观察期建议至少 7 天且覆盖一次完整使用/导出流程；到期由实际使用者确认退役旧站。备份保留期限另行约定，不自动删除旧库。

## 5. 已确认的交互方向

采用 **方案 A：延续 Planner 现有交互架构**。保留顶部四模块入口、电脑排座三栏、浅色背景和柔和粉色点缀。不再比较 B/C，不单列视觉重构项目，也不要求将预览 HTML 搬入生产或随本文复制。

迁移：完整分页、不漏删除、保留同名不同人、映射可追溯、字段不截断、原图片可用、最终冻结后重导出、同一批次重跑不重复；未知状态和坏引用有人工处理记录。

产品：原 Excel 列和住宿汇总一致；Konva 桌位姓名/人数/出席显示准确；真实浏览器检查桌面与触摸操作、缩放、刷新及完整场地导出；按实际数据量与至少 150 人样本验证布局。在 Planner 引入适用的领域/Repository 测试与四模块浏览器回归；Seating 的 SVG getBBox 或 Pointer Events 专项测试只有迁入对应实现时才沿用，不能替代 Konva 验证。

每个新实体 revision 从 0 开始；每次成功改变实体内容加 1；一次核心命令使 snapshotRevision 加 1。笔记使用自身 revision，不因改笔记强制增加核心序号。新增实体不得复用已删除 ID；从回收站恢复同一实体允许保留原 ID，但 revision 必须高于该 ID 的历史版本，回收记录只可成功恢复一次，不能把旧请求重新变成合法写入。整项目恢复则更换 dataEpoch。数量、字符串长度、图片大小和核心文档预算在 P0/P1a 测量后写入一份共享限制配置；达到限制明确报错，不截断旧记录。正式迁移前该配置必须有具体值和样本依据。

业务不变量与默认行为：

- tableId 与 seatIndex 同时为空或同时有效；座位在容量内且唯一。待确认宾客允许排座；不出席宾客排座返回明确错误，先由用户修改出席状态；重新确认不自动恢复原座位。
- 移桌、移出座位和删桌不改变出席；标为不出席原子释放座位，保留住宿。宾客删除同时移除该宾客自身的全部关联。
- 缩小桌容量若导致任何现有 seatIndex 越界则拒绝，不自动重排；需要先明确调整座位。非空桌使用“移出宾客并删桌”命令。
- 一位宾客所有晚次对应同一个 roomId，同房宾客独立选晚次，不自动补连续日期。
- stayNeed 独立于出席；分房设为 needed，单纯移出房间或删房不自动改为不需要。有房间时 stayNeed 必须为 needed；不能通过通用更新把已分房者改成 pending，应先明确移出房间再修改需求。已有房间改为 not_needed 时先确认，再原子清空房间/晚次并生成恢复材料；取消确认不修改任何状态。旧数据有房设 needed，无房设 pending。
- 待安排房间 = needed 且未分房；需求待确认 = pending；晚次待定 = 已分房且无晚次。出席状态另行展示，不隐式改写需求。
- roomId 为空时 stayDates 必须为空；有房无晚次允许保存。晚次为有效 ISO 日期、去重排序且属于项目选项。删房清空关联和晚次；删晚次清除所有相关宾客的该日期，均原子完成。
- 房间全部日期视图：任一已选晚次人数超过建议容量即提示，并显示日期；无晚次宾客标注“晚次待定”，不凭空计入某晚，也不宣称容量已充分验证。按晚视图保持当晚口径；已安排住宿总人数仍按 roomId 计数。
- 新增/更新表单只传白名单字段；不能通过通用 patch 更改 ID、projectId、revision 或绕过排座/住宿命令修改关联。

### 9.3 命令、并发与回执

统一请求包含 `projectId`、`operationId`、`commandVersion`、`type`、`payload`、`expectedRevisions`。请求还绑定 dataEpoch 和已验证的访问会话；权限由服务器校验协作/管理凭证得出，不能信任请求自报角色。首期命令覆盖 guest.add/update/delete/assign/unassign/swap、table.add/update/deleteWithGuests、room.add/update/deleteWithAssignments、guest.assignRoom/setStayDates/setStayNeed、project.update、group.add、stayDate.add/remove、note.add/update/delete；轻量历史增加 recycle.restore、snapshot.create/restore 等专用命令，recycle.restore 与 snapshot.create 允许协作权限，整项目 snapshot.restore 需私有管理权限；项目入口增加 project.create 及凭证校验/轮换接口，轮换需管理权限；重排仅在对应交互接入时启用，批量导入走受控迁移入口，不暴露通用快照覆盖接口。

并发采用“核心文档事务 + 业务实体预期版本”：

- snapshotRevision 用于订阅去旧和提交排序，不要求每个普通命令携带整项目预期版本；不同宾客的无关联修改在事务重试后可分别成功。
- 普通修改检查对应实体 revision；排座检查宾客及目标桌 revision，并在事务内重新检查座位占用；交换检查双方宾客及相关桌；同座竞争只能一方成功，不能自动换到另一个座位掩盖冲突。
- 重排、删桌、删房、删晚次等涉及整组对象的操作，检查用户确认时的完整受影响 ID 集合及 revision，新增关联也算冲突；提示重新确认后才执行新的意图。
- 表/房/配置 revision 用于相应内容变化；宾客关联变化增加宾客 revision，服务端仍从最新核心文档验证引用、容量和完整集合，不能只依靠父对象 revision。
- 数据库事务竞争可有界重试；业务 revision 冲突不自动换成最新 revision 覆盖。SDK 重试能力、上限和事务支持以 P1a 实测记录为准。2026-10-04 目标环境实测同一事务内并发读取返回 TransactionBusy，因此事务内部顺序执行读写；不同事务的并发争用仍须验证。

成功返回 operationId、完整冻结命令规范化 JSON 的 SHA-256 requestDigest、服务端提交时间、受影响实体版本，以及核心 snapshotRevision 或笔记 revision。错误至少区分 INVALID_INPUT、NOT_FOUND、FORBIDDEN、CONFLICT、SEAT_OCCUPIED、CAPACITY_TOO_SMALL、OPERATION_ID_REUSED；客户端传输超时单列为“结果待确认”，不能伪装成确定业务失败。

回执键绑定 projectId、dataEpoch 与全局随机 operationId，并记录规范化请求摘要和请求来源元数据；不能把可变化的匿名 SDK 身份放进唯一去重键，否则换会话可能重复提交。查询/重试仍须当前有效项目授权；客户端核对 requestDigest 与本地冻结命令一致才移除草稿，不匹配保留草稿并报失败。来源元数据不代替授权。事务中先检查授权及已有回执；同 ID 同摘要返回原成功结果，同 ID 不同摘要拒绝；业务变更与成功回执一同提交。提供受权限约束的回执查询，以便响应丢失后确认结果。当前有效项目授权可按原 dataEpoch + operationId 查询旧代次已有回执；该查询不允许执行旧代次业务写入。整项目恢复的回执保留在原请求键下并返回新 dataEpoch，使恢复成功但响应丢失也可核验；不存在回执时不能据此重放旧代次命令。业务变更、成功回执、当天活动增量及适用的回收材料同事务提交。首期不自动清理成功回执；若后续增加保留期限，须同时定义过期操作禁止盲目重放的规则。

### 9.4 队列、订阅与项目切换

客户端分开保存最后确认快照与待提交意图，页面乐观状态由两者计算，远端订阅只能更新确认快照。每项目串行发送；新增实体预先分配稳定 ID，使随后排座/分房可引用它。依赖前一条本地操作的意图，在前条成功后取其回执版本形成请求；不能用远端新版本自动改写一次已经冲突的用户意图。

请求首次发送前，先将冻结的完整请求、operationId、dataEpoch 与“待确认发送结果”状态原子持久化，再发送网络请求；本地落盘失败暂停发送并提示，不能先发出后补记。重启时无法判断是否发出的请求也用原 ID 核对回执，禁止重新生成 ID。请求一经进入此状态即不修改内容；超时先查询回执或以完全相同请求重试。成功后移出队列；同页重连先处理结果待确认请求，再自动提交无冲突的队列；重新打开页面先展示本机草稿，由使用者确认恢复并同步或放弃。放弃不能撤销已成功提交操作。确定失败时重新从确认快照计算界面，保留失败草稿，暂停该项目后续队列，由用户重试或放弃。依赖失败新增实体的动作必须一起标明，不能继续发送。修改失败请求内容视为新的意图，使用新 operationId。

保存反馈分别表达本地持久保存与云端提交状态：至少区分“正在保存本地草稿 / 草稿已保存在本机，尚未同步 / 正在同步 / 已同步到云端 / 云端结果待确认 / 冲突待处理 / 本地保存失败 / 无权访问”。离线或错误作为附加原因，不把本地保存成功显示为云端成功；按项目显示待同步数量。订阅先于回执到达也不能把未确认命令再次乐观应用；P1b 必须验证这一时序，必要时等待对应回执后再重放队列。

切换项目先取消订阅并增加本地加载代号，忽略旧异步加载结果；旧队列继续绑定旧 projectId，不重新定向。存在待保存内容时显示所属项目和数量。权限失效停止该项目发送、订阅与轮询，清除可展示的远端缓存，待处理草稿按项目、稳定本机草稿来源标识及数据代次保存在本机；本机来源标识不等于临时匿名 SDK 身份，也不是权限凭证。重新获得该项目有效凭证后允许使用者明确恢复；已发送请求仍按原 operationId 核对回执，不能因换链接或会话而生成新 ID 盲目重放。

首期必须持久保存本地草稿，覆盖刷新、重新打开和手机切后台后的恢复；包括未发布笔记正文及选图，不能只保存已经点击提交的命令。实际写入本地成功后才显示本地已保存；容量不足或写入失败要持续提示。本地草稿不等于备份，清除浏览器数据、无痕会话或设备丢失不能承诺恢复。关闭提醒仅为辅助，不能把 beforeunload 当作保存保证。旧 localStorage 先备份并按来源项目归属导入；新缓存按项目及本机草稿来源隔离，使用前检查当前访问授权，“我的项目”仍是个人入口，不混入共享配置。

### 9.5 分享链接授权与图片访问

首期不注册账号，不建立成员列表、逐人权限或邀请审批；持有效长随机分享凭证即获该项目查看和编辑权，转发链接即转授同等编辑权。内部 projectId 仅定位项目，旧 8 位项目 ID 不直接作为长期编辑凭证。

服务器校验分享凭证与项目的绑定。若底层需要匿名身份，仅用于会话及请求归属，不作为已获项目权限的证明。凭证可以兑换受限会话，但其有效性仍绑定当前分享凭证版本；更换链接时，旧凭证及其派生会话都失效。创建者保管独立私有管理链接，可更换协作链接及执行整项目恢复；普通协作链接不能调用这些管理命令。管理链接与协作链接使用独立凭证，不是 URL 中自报 role=admin。链接均遗失时的受控人工找回流程在平台验证阶段落实。

权限矩阵如下；私有管理能力是独立凭证的范围，不是实名账号或成员角色：

| 入口 | 查看/编辑、保存版本、恢复回收站 | 整项目恢复、换协作链接 | 数据库直接写/查看管理凭证 |
| --- | --- | --- | --- |
| 无效或无凭证 | 拒绝 | 拒绝 | 拒绝 |
| 有效协作链接 | 仅本项目允许 | 拒绝 | 拒绝 |
| 有效私有管理链接 | 仅本项目允许 | 仅本项目允许 | 拒绝 |
| 受控运维通道 | 限批准的维护范围 | 迁移/灾难恢复另行执行 | 云端运行密钥不进入前端 |

创建项目必须真正生成独立数据与两类凭证，重复新建请求幂等。首期创建协议由客户端使用密码学安全随机数生成创建请求 ID 和两类独立秘密，先可靠保存在本机，再经受保护接口提交；服务端仅保存凭证摘要及创建请求绑定，重试校验同一请求摘要并返回同一项目，不另建项目或更换秘密。创建成功响应丢失时仍可用原请求完成交付；秘密不进入遥测和普通操作回执。P1a 验证安全存储、随机数及此无项目授权入口的限流；未知项目网址不自动新建。为朋友代建时明确交付两条链接，朋友保管管理链接，平台日常页面不默认展示其业务。已取得管理链接者技术上仍有管理能力，不宣称“交付后自动忘记”；需要撤销旧管理凭证时走受控轮换，不引入成员交接页面。

应用不得返回凭证摘要或通过协作接口返回管理链接。敏感凭证不进入日志、导出、快照和错误报告；按部署方式选择链接编码与访问策略，验证不会泄漏到第三方资源请求。轮换凭证与写入通过事务中的凭证版本校验确定先后，失效后的新请求必须拒绝。平台云账号运维者技术上可能访问数据，不宣称对其密码学不可见。

业务、权限/凭证摘要、回执与历史数据禁止客户端直接写。读取及订阅只有在能验证当前项目访问权时开放，否则使用鉴权云函数读取/轮询。图片上传、查看、引用与删除同样检查项目；不能把图片或历史数据作为无需授权的旁路。 2026-10-04 实测：PRIVATE 规则下，匿名调用者可直接获取其经云函数上传的文件链接，因此 PRIVATE 不足以实现项目级隔离；业务图片命名空间须禁止客户端直读直写，或使用经验证的等效隔离，再由鉴权接口交付内容/短时访问能力。具体失败证据及修复验证见开发验证记录。已经下载的内容无法远程收回，临时文件链接的有效期与撤销边界需实测。

P1a 以 A 项目有效链接、B 项目有效链接、无凭证、错误凭证、已失效凭证分别测试列表查询、读取、写入、订阅、回执与图片；验证更改 projectId 不会越权。实际 SDK、环境类型、限制和延迟以测试记录为准。分享凭证不进入日志、历史记录或导出文件。

### 9.6 迁移工作表与发布控制

P0/P3 产物格式固定为以下字段；真实数据文件保存在受控目录，仓库只存虚构样例和汇总：

- 来源清单：sourceSystem、sourceProjectId、schema、exportedAt、sourceHash、分页覆盖、实体数、图片数/字节数、本地状态来源、异常数量。
- 映射表：sourceSystem/sourceProjectId/entityType/sourceId、targetId、batchId、disposition（保留/批准合并/人工排除）、decisionId。人工排除仍保留源备份和理由。
- 冲突决定：conflictId、相关来源引用、字段、候选值、最终决定、确认人、确认时间。不能只保存“已处理”标记。
- 对账报告：源覆盖率、目标数量、引用/座位校验、字段差异、按晚统计、图片校验、未解决项、输入及输出哈希。

Seating v1 专用转换保留 pending/confirmed/declined，映射 relationshipGroup→group、note→notes、name/capacity→label/seats；来源 side 保留。Planner 不存在的字段用明确默认值并记录。两边同人候选的出席和桌位仍由人工决定；Seating 的 canvas/anchor 不直接覆盖 Planner 舞台和坐标。核心版本与实体 revision 重新初始化，来源时间单独追溯。

迁移批次需有 prepared/importing/verified/published/failed 状态及源哈希绑定；目标不可见通过授权/发布状态执行，不仅隐藏菜单。重复导入先检查批次与目标版本，已有人工修改则停止覆盖。图片对象和数据文件都进入批次清单，失败批次不得自动删除共用对象。

原工作流 push main 会部署 GitHub Pages；2026-10-05 工作区已改为手动触发、main SHA 精确校验、必填配置与独立发布作业，尚未在远端执行。P1/P2 仅在功能分支及独立测试入口运行；前端环境和云函数环境必须显式配对，缺失配置直接报错，不能回退生产。第一次让融合代码进入 main 之前，必须将发布拆为受控部署或加入明确的环境批准步骤，并验证实际入口是否确实使用该工作流；现有 Vercel/其他托管配置也需要盘点，不能仅根据仓库文件猜测生产入口。

切换前登记前端构建版本、云函数版本、schemaVersion、迁移 batchId、目标环境和旧端停写证据。旧端停写在数据库/后端权限执行；保留旧权限配置作为受控恢复材料。P5 才决定正式发布与停写时间，不因开发分支改名或文档提交触发发布。

### 10.1 接入前必须解决的缺口

| 编号 / 角度 | 触发场景与后果 | 处理与验收 |

| A1 操作原子性 | `SeatingPage.tsx` 的 handleDrop 连续调用两次 assign。原样适配新校验后，第一步因目标座位被占而失败，换座功能退化 | 明确动作映射：移到空位用 assign，占用位交换用 swap；不能仅替换 store 内部保存函数。测试同桌/跨桌交换、空位移动及对方同时编辑 |

| A7 数据顺序 | Planner 数组迁为 ID 字典后，原名单顺序和导出行序可能变化；笔记同时间排序也可能跳动 | 持久化明确的宾客/桌/房显示顺序，迁移按核对后的源顺序初始化；增加/删除在同一命令维护顺序和实体。服务端验证无重复和悬空 ID；笔记使用 createdAt + ID 稳定排序。不因使用 Record 就依赖数据库字段顺序 |

A2 的 notesRevision 可放在项目笔记元数据文档中，不要求每次笔记操作重写核心婚礼文档；轮询失败保留“最后读取结果 + 未刷新”提示，不能把读取失败解释为项目或笔记已删除。若实测能以更简单的服务端一致性读取实现相同保证，可在 P1a 后替换具体读取方式，但保留完整性验收。

### 10.2 产品与数据语义遗漏

1. **所属方存在双重事实。**当前 `exportGuests.ts` 只按 group 中的“新郎/新娘”推断所属方，忽略新 side。因此“同事 + bride”导出为空，“新郎亲属 + bride”会相互矛盾。约定显式 side 优先；unset 时才按旧规则回退，shared 显示双方。分组原文不因 side 被改写；显式 side 与分组前缀矛盾时提示并保留原标签，不能机械去前缀掩盖冲突。为旧数据、unset、shared、冲突样例固定导出预期，保持原七列。
2. **日期展示不能当存储键。**当前住宿 Excel 用 formatNight 的月日结果作为列键；2026-10-02 与 2027-10-02 都变成 10.2，会覆盖一列。已用最小字典复现验证碰撞。内部一直按 ISO 日期索引；同一项目跨年时显示带年份的唯一列标题，单年保留原格式。
3. **住宿单房模型已确认。**每位宾客所有所选晚次住同一房间，不支持逐晚换房。同一房间不同宾客各自选择晚次，允许不同日期到达；不能把 roomId 相同理解为 stayDates 必须相同。
4. **分房未选晚次的人不会出现在每晚名单里。**不自动补晚次的原则保持，但导出前提示“有 N 人已分房但晚次待定”，避免使用者把酒店用房表当完整住宿名单；不擅自改变既有两张表结构。
5. **空舞台位置具有设备相关语义。**当前 Konva 以视口宽度决定默认舞台位置与宽度，不同手机和电脑并不展示同一个默认场地。需要明确固定场地坐标与个人视口的边界：项目保存世界坐标，缩放/平移仅本地；旧 null 在迁移核对时选定基准布局并记录，不能取第一位访问者屏幕随意固化。若保留自适应舞台，必须明确它不是共享固定坐标，导出也使用一致基准。
6. **手机可用性不能只检查画布。**现有换座使用 HTML 拖放，笔记删除/移除图片依赖 hover。首期至少提供手机可点击的选人换座、删除确认和图片移除入口；iPhone Safari、Android/微信内置浏览器分别实机验收。Chromium 触摸模拟不等于微信实机通过。

### 10.3 迁移、恢复和运维补充

- **最终冻结必须同时覆盖两个来源和本地草稿。**Supabase、Seating CloudBase 均在后端停写后等待在途请求结束，再完整分页导出。未保存浏览器修改单列处理，不盲目把本地快照当最后真相。跨表导出不能在持续写入时宣称是一致快照。
- **停写范围不能误伤朋友项目。**先列出各来源实际项目与使用者，按项目冻结；若旧权限只能整库停写，先迁移全部受影响项目或明确协调窗口，不能用全库只读完成单场婚礼切换。停写后用旧客户端请求验证，而非只看控制台配置。
- **新备份必须覆盖完整恢复单元。**除核心数据，还包括笔记、对象文件清单/内容、权限与项目映射、版本、回执；凭证等敏感备份单独控制访问。备份读取须有一致边界。P5 前在隔离项目实际恢复一次，核对图片和按晚统计，并验证旧请求不会污染恢复后的项目。
- **切换后的新写入不能靠猜差异回滚。**成功回执并不等于可完整重放的业务日志。恢复方案需要明确实际可用材料：切换时基线、当前全量快照、删除与来源映射；反向转换工具未验证前，新版已有写入只允许停写修复新站，不承诺能快速退回旧库。
- **持续备份与事故响应不止观察 7 天。**上线前记录备份频率、保留期、可接受数据损失时长、恢复时长和操作负责人；具体数值待使用者确认。首期用托管能力或简单导出即可，不建设完整运维平台。监测持续保存失败、权限拒绝异常、备份失败和资源用量；日志只记录项目/操作标识、耗时、版本和错误码，不写姓名、电话、正文或令牌。
- **预算与防滥用覆盖全部入口。**不仅分享凭证校验限流，还包括匿名新建项目、图片上传和回执查询；限制每次载荷、项目数量、存储占用与重试频率。轮询按页面可见性与退避策略运行，避免多人多标签页持续传整份快照。阈值依据实际规模确定，不能无依据卡住原业务。
- **图片上传中和删除后都要可恢复。**客户端保持用户选图顺序，不以异步上传完成顺序排列；部分上传失败保留正文与草稿，重试不重复创建笔记；移动端图片方向、支持格式、超限提示与临时链接过期纳入测试。

## 11. 轻量历史、恢复与筹备日历

### 11.1 保存与版本的边界

当前状态同步与可恢复版本分别处理：自动同步仍持续运行，“保存版本”仅生成一个可命名的恢复点，不决定别人能否看到修改。

| 行为 | 当前状态 | 额外保留 |
| --- | --- | --- |
| 移动桌子、常规字段编辑、排座与晚次调整 | 完整动作提交后自动同步；离线保留本机草稿 | 更新当天活动计数，不生成独立可见历史版本 |
| 单个新增宾客/桌/房/笔记 | 自动同步 | 计入当天活动；不为每个新增复制整个项目 |
| 删除宾客/桌/房/笔记、删除晚次或清除住宿安排等有损动作 | 按现有确认与原子规则提交 | 同事务写入可恢复的删除/清除记录，保留关联和必要的修改前内容 |
| 手动“保存版本” | 不改变现有业务内容 | 对已同步的固定项目状态保存命名快照；有待同步内容时提示，首期不把私有草稿混成共享正式版本 |
| 有改动的一天 | 持续同步 | 生成一份自动项目快照；无改动日不重复复制 |
| 批量导入/替换、整项目恢复 | 预览并明确确认后执行 | 操作前自动保留安全快照，防止大范围修改无法退回 |

有损动作的首期白名单为 guest/table/room/note 删除、stayDate.remove、移出房间（assignRoom(null)）及已有住宿时改为 not_needed。普通 setStayDates 调整、换座、移出座位和字段编辑不产生回收记录；批量删除按一次命令保留一个恢复包。前端显示具体将清除的内容，服务端按命令类型生成材料，不能用“所有字段变化都算有损”把回收站变成逐操作日志。

此方案提供删除找回与指定快照恢复，不提供普通字段在一天内的逐次历史。比如电话上午从 A 改为 B、下午改为 C，若 B 未进入任何手动/每日快照，就不能承诺单独恢复 B。若使用者需要这种能力，再增加限定字段的修改历史，不能悄悄承诺“所有历史更改均可查看”。

回收站不能只保存被删的桌子/房间本身：要记录当时受影响的宾客及关联；恢复时依据当前状态预览可恢复项，不抢占已被别人使用的座位、不覆盖之后重新安排的房间。已重新创建/编辑的数据出现冲突时先选择处理；清除住宿安排虽不是删除宾客，也需要可恢复记录。图片由当前业务、回收站和快照共同引用，仍有任一引用时不能自动清理。回收站保留 30 天，自动每日快照保留 90 天；手动命名版本不自动删除。到期仅移除相应恢复入口/记录，仍被当前业务或其他有效版本引用的图片不得删除。删除/清除动作与其恢复材料、回执必须同事务提交，失败时整体不生效。

### 11.2 筹备日历与每日快照

- 统计整个婚礼项目的协作活跃度，不冒充每位真人的贡献；在持链接授权下无法可靠认定真实操作人。
- 使用服务器提交时间，按 Asia/Shanghai 分日。每个完整成功且有实际变化的操作只计一次；拖动中每帧、重试、打开页面、系统备份均不计。未同步本机草稿不计入共享热力图。
- 每项目每天一条小型汇总，包含总操作数及宾客/排座/住宿/笔记/布局分类。一次批量新增可显示“新增 20 位”，同时区分操作数与影响人数。颜色表达活跃程度，不代表安排完成度；布局可单独展示，避免看成新增人数。
- 点击日期打开侧栏，显示当天新增/调整/删除汇总、该日自动快照及手动版本。提供快照预览、导出和经过确认的恢复入口；汇总不能展开为不存在的逐次日志。
- 今天显示截至目前的活动和当前云端状态，自动日快照尚未生成时明确标注，不把活动颜色当成快照成功标志。无快照、生成失败、已过保留期均区分显示；手机支持点击，颜色之外提供文字计数。
- 每日快照保存该活跃日最后已提交的业务状态。服务端定时任务与跨日首次业务写入共用日结入口：若上一活跃日尚未封存，先固定其核心/笔记版本及文件引用，再允许下一日写入；无改动日不补空快照。浏览器关闭时定时任务仍可执行；任务延迟由后续写入前的检查兜底，不拿次日已修改状态冒充前一天。以 projectId + 业务日期幂等，记录业务日期、最后业务提交时间、真实 capturedAt；后者可能在次日。所有核心/笔记业务写入口在提交事务内校验服务器业务日期及日结状态；跨午夜的在途请求重试时重新判定，不能只在函数入口检查一次。短暂日结期间新写入等待/可重试，本地草稿继续保存；固定一致版本失败不得越过日结写入后再伪造补拍。P1a 验证这一跨核心/笔记写入屏障及超时恢复，P2 接入任务与提示；每天只封存一次，不为每次拖动复制项目。记录日结等待耗时与失败恢复结果；若实测无法满足保存反馈目标，先讨论调整日快照语义或实现，不静默改为漏拍前一天。

### 11.3 存储与资源边界

- 云端当前数据仍有正常写入；免去逐操作全量快照不等于零成本。活动计数是每天固定一条汇总的更新，幂等回执仍单独保留，不能为省日志删除重试保护。
- 存储主要随活跃天数、手动版本数及删除数据量增加；图片不按快照重复复制。快照生成、跨日日结检查与活动计数有额外读写，保留期由使用者确认，体积和负载通过实测验证；需要调整已确认保留承诺时重新讨论。
- 此方案不引入事件溯源、任意时点重放或完整 Git 式分支/合并。快照只包含业务数据，不包含可复活旧链接的权限凭证；恢复仍绑定当前授权并防止覆盖预览后的新修改。
- CloudBase 可用定时触发器承载每日任务；具体配置与故障重试在目标环境验证。[官方定时触发器说明](https://docs.cloudbase.net/cloud-function/timer-trigger)

### 11.4 保留期限与清理

- 回收站自删除/清除起保留 30 天；自动每日快照自生成起保留 90 天，界面显示到期时间。手动命名版本不自动删除；安全快照默认按自动快照保留期处理，使用者可通过保存命名版本保留需要的状态。
- 90 天控制自动快照存量，不会使每次编辑额外复制 90 份。按最多一项目一活跃日一份计算，自动快照正文占用约为项目数 × 90 × 平均单份快照字节数；还要另计索引、元数据、回收站、手动/安全版本和保留图片。
- 性能验证区分三项：日任务的读取/写入耗时，90 天存储体积，历史页按项目/日期分页读取。正常页面不读取全部历史；无变化日不生成重复快照；定时生成与到期清理采用限并发/分页批次，避免集中处理所有项目。
- 示例仅作容量估算：每份 500 KB，90 份约 45 MB；10 个每天活跃的项目约 450 MB（十进制，未计索引等）。真实大小必须以 P0/P1 样本测量，不能把此例视为项目实际占用或价格承诺。图片不重复复制，但历史引用会延长原文件的保留时间。

### 11.5 快照一致性与恢复流程

- 项目快照包含完整核心数据、全部笔记内容或不可变笔记版本引用、图片引用清单、显示顺序、schemaVersion、dataEpoch、snapshotRevision、notesRevision 与真实 capturedAt；不能只备份排座。用于恢复的记录不含分享/管理凭证、访问会话、旧操作队列或可回放的旧回执。
- 读取核心与分页笔记前后校验上述版本组；发生并发修改则有界重试，失败不发布快照。快照标记 building/ready/failed，只有 ready 且引用文件验证通过才可作为恢复点。任务重复触发按项目/日期或 operationId 幂等。
- 整项目恢复只对管理凭证开放：选版本→预览影响→确认→先保存当前安全快照→提交恢复。提交前再次检查预览版本，期间有新编辑则重新预览，不静默覆盖。恢复成功更换 dataEpoch、通知各端重载；本机旧草稿保留待人工核对，不能自动重发。
- P1a 验证跨核心与多笔记文档的原子恢复能力；超过事务限制时，采用隐藏的新数据代次准备完整副本，校验后原子切换当前代次。失败时原代次仍为唯一可读写状态，不逐批覆盖用户可见文档。“每项目一份核心文档”指唯一当前生效版本，允许隐藏的准备代次及待清理旧代次；核心与笔记读写均校验当前代次指针，不能切换核心后继续读旧笔记。具体文档键和切换方案由验证确定，不能以“逐个写完”代替恢复原子性。
- 单条回收站恢复也要预览关联冲突、验证当前版本，并与回收记录状态及回执原子提交。恢复同一记录不能重复创建；不抢占别人新安排的桌位/房间。恢复后的实体版本见第 9.2 节。回收记录绑定来源 dataEpoch；整项目恢复后旧代次记录仍按原 30 天期限保留、可预览/导出，但标明“来自恢复前的项目，不能直接恢复”，首期不增加跨代次自动合并。
- 业务快照只恢复核心业务与笔记/图片引用，不回滚活动汇总、历史目录、回收站状态和成功回执；恢复本身计为当天一次操作，不把旧活动再计入当天。不能撤回链接轮换或复活旧凭证；历史也不等于独立灾难备份。所选快照 schema 不兼容时先转换并验证，不能强行写入当前模型。
- 到期清理和恢复/保存版本并发时必须互斥领取相应资源；只有已过期且无有效业务/草稿上传租期/回收站/快照引用的文件才可清理。清理失败可重试，不能以删除文件先于引用核查。

### 11.6 完成条件

在第 7 节 V5–V7 留下验证记录：拖动多次只同步当前状态；失败/重试不重复活动计数；删除及回收材料原子提交；恢复不覆盖后续安排；30/90 天边界及手动版本保留通过模拟时间测试；仍被引用的图片可用；重复日任务不重复生成快照；缺失、失败或过期快照如实显示；整项目恢复不恢复旧凭证、旧草稿不覆盖新代次。
