## 一、诊断结论

| 编号/优先级 | 用户观察 | 排查结果 | 原因与范围 |
| --- | --- | --- | --- |
| U1 / P1 | 点击桌子前后舞台和囍字移动 | 实际页面复现：画布宽1168→880，默认舞台x584→440、囍字x484→340，各左移144px；桌子世界坐标150/200保持不变 | 桌详情栏占用288px，ResizeObserver更新视口尺寸；默认舞台和水印却用视口宽计算世界坐标。属于布局/坐标混用，复现中不是桌位数据改写 |
| U2 / P2 | 房间排列没有可理解的顺序 | 将虚构前3房号设为008/002/001，页面仍按此顺序显示；新增房位于末尾 | 页面仅筛选、不排序，PageStore按roomOrder映射；迁移按来源id读取后保留该顺序。因此UUID顺序不是房号/房型顺序，新建则追加；并非前端每次随机洗牌 |
| U3 / P1 | 添加大床房后需滚到最下面，再添加人和日期 | 30房夹具新增“大床房31”在首屏以下，没有自动打开选择器；选择器中没有日期控件 | 页头按钮只调用addRoom，没有衔接pickerRoomId或滚动定位；日期被拆成分配后回房卡再选。默认房号由全部房间总数+1生成，也不是各房型独立编号 |
| U4 / P1 | 添加宾客搜索不到未分房的人 | 已确认出席、未分房、stayNeed=pending的虚构宾客搜不到；同样未分房但stayNeed=needed的宾客能搜到 | GuestPicker先限制stayNeed为undefined或needed，再按姓名/分组/电话搜索。实际根因是住宿需求预过滤，不是roomId过滤，也不是CloudBase漏数据 |

关键关联：Planner迁移中，有房者映射stayNeed=needed，无房者映射pending，以免猜测住宿需求；新建宾客也默认pending。现在过滤器将这些人全部排除，造成“只能搜到以前分过房的人”的体验。出席、住宿需求、房间和晚次是不同事实，不应为让搜索可用而批量修改真实名单。

舞台补充：已有mainStagePos时中心不再随stageW变化，但舞台宽度仍用min(stageW×0.35,260)，窄画布会变宽窄；囍字始终依赖stageW/stageH。不得只固定默认x，遗漏已保存舞台、缩放和平移后的尺寸或水印行为。

## 二、建议实施顺序与完成标准

### 第一阶段：U4搜索范围与U3住宿操作闭环

1. 宾客选择器默认搜索全名单，提供“全部 / 已确认出席 / 需要住宿 / 未分房”的明确筛选；姓名、分组、电话匹配保持一致。显示出席、住宿需求、当前房间和个人晚次，不用出席状态推断住宿需求。
2. 已在本房的人标为已安排；已有其他房间的人标为移入，操作前说明将更换原房间。住宿待确认/原不需要者均可被找到，明确执行安排住宿时再设为needed；不把全名单先批量改成needed，不默认确认出席。不出席者仍保留可搜索及状态提醒，不发明服务端没有的出席硬门槛。
3. 页头添加房间：房间创建确认成功后，立即打开该新房的宾客与个人晚次弹窗，自动聚焦搜索；新房不被当前房型筛选隐藏。取消弹窗保留已建空房并清楚提示，不自动删除。实际实现需取得本次创建房间id，不能猜测“数组最后一个”，以免并发协作错房。
4. 弹窗支持为每位选中宾客选择项目内的住宿晚次；当前日期筛选只能作为可确认的建议，不自动套给所有人。完整ISO日期及跨年提示明确，允许主动保留“晚次待定”。重新安排已分房者，已有个人晚次预填并需用户确认，不悄悄清空。
5. 选人和日期一次确认保存。首选必要的最小原子安排命令，校验宾客/房间/配置revision，统一设置roomId、stayNeed和个人stayDates；沿用现有请求冻结、回执、草稿与冲突机制，不另造同步层。现有assignRoom会自动设needed，但setStayDates是另一个命令，直接串联而笼统显示成功会留下“房间已变、日期未存”的部分成功。
6. 每晚用房/超建议容量继续按个人晚次计算，显示已有警告；不同晚次可以复用房间。零项目日期时允许创建空房/明确晚次待定，并提供设置项目日期入口，不伪造日期。

验收：全名单、已确认及其他筛选可切换；pending未分房、needed未分房、其他房间、本房间、同名不同人、前导零电话均有虚构用例。134/150人及至少30房时，新房按钮一次操作进入弹窗，无需到页尾；确认后的宾客/日期刷新和另一个浏览器回读一致。网络失败、日期配置被删除、宾客被他人改动、重复点击不能产生假成功或重复房间；取消不改变宾客。390px与真机软键盘/滚动/触摸分别验收。

### 第二阶段：U1画布坐标稳定

1. 世界中的舞台采用稳定坐标和尺寸，视口只承担显示宽高、缩放与平移。缺省舞台是可重复的世界坐标缺省值，不随每次选桌重新计算；不为一次点选隐式写入云端布局，不任意重排迁移桌子。
2. 桌详情栏优先覆盖或占据稳定保留区域，避免选中/取消时整幅安排跳动；确需改变视口尺寸时，明确保持原视图的世界锚点。
3. 囍字为装饰，建议放在独立屏幕装饰层，保持画布视图中的稳定锚点；禁止用变化后的屏幕尺寸重新生成内容层世界坐标。导出单独固定构图，不把详情栏是否打开带入导出结果。
4. 拖舞台、滚轮缩放、定位适配、移动端详情抽屉和导出共用清楚的坐标规则；已有mainStagePos必须原样保留。

验收：在固定浏览器窗口内，连续打开/关闭不同桌详情，舞台/水印不突跳、桌位不变、项目配置不产生写入。覆盖mainStagePos=null与已有坐标、20%/80%/100%/放大、平移后点选、窄屏抽屉、窗口缩放；PNG在相同固定构图下不因选桌状态改变布局。使用真实Chromium/Konva几何及触摸验证，不能只测纯函数。

### 第三阶段：U2房间顺序与默认命名

1. 建议默认按房型分组（大床房/标间），组内按房号自然排序，展示排序说明；含数字的1/2/10不能按字符串排成1/10/2。非数字房号保留可理解的中文排序，重名用稳定id兜底。
2. 排序先作为显示层行为，不改旧房id、关联或来源provenance，不整批重写roomOrder。浏览器/筛选/刷新/第二客户端必须一致；新建后即使排序位置在中间，仍直接进入该房弹窗。
3. 默认命名按同房型已有命名找可用编号，避免用全部房间总数+1生成“大床房15”；保留用户手工命名及001前导零，不自动重命名已有房间。手工拖排序未在本轮反馈要求中，不扩展为新领域命令。

验收：混合房型、1/2/10/001/中文/重名、改名后、删除重建、筛选后及两客户端显示一致。原始房号和宾客关联完整保留。房号展示排序只用于房卡，不能改变个人住宿晚次或覆盖率统计。

以上默认全名单及房型/房号排序是建议产品选择，用户尚未明确唯一规则；实施前如用户选择另一规则，应更新该文档后实施，不把本诊断当作已批准的业务改动或已完成修复。
