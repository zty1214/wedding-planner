# 150 人与 90 天历史本地规模验收

本轮只使用本机 MemoryStore 和纯虚构数据，不连接 CloudBase、不修改真实项目。原始结果见 [JSON](2026-10-05-scale-local.json)。

## 可复现入口

```sh
npm run test:scale
# 保存含本地耗时和逻辑事务调用计数的完整报告：
node --experimental-strip-types scripts/fusion/validate-scale.ts /tmp/planner-scale.json
```

`npm run check` 已纳入此场景；融合类型检查也检查该脚本。样本为 150 位具体宾客、15 张 10 人桌、30 间标间、12 篇各 2,002 字的笔记。60 人住宿，每间两人中一位住跨年两晚、一位仅第二晚到达；保留姓名数字后缀和电话前导零。初始化结构由脚本生成并通过 assertCore，后续 90 次移动桌子、12 次新增笔记、日结、读分页和恢复调用实际服务实现。

| 项目 | JSON UTF-8 字节数 |

| 当前核心（含版本封装） | 46,516 |
| 12 篇笔记数组 | 73,997 |
| 单份自动快照正文 | 120,884 |
| 90 份自动快照正文总计 | 10,879,722 |
| 90 条历史元数据索引 | 33,832 |
| 最大历史分页响应 | 7,566 |
| 最大命令请求封装 | 6,366 |
| 宾客 XLSX | 64,930 |
| 住宿 XLSX | 25,030 |

90 份历史分 5 页完整读取，无重复、遗漏；整项目恢复后的 core 与笔记逐项等于目标快照，同时生成安全版本、变更 dataEpoch，当前访问凭证不变。Excel 实际生成二进制后再解析，确认 150 行、前导零电话、姓名后缀、跨年日期，以及第一晚 30 人、第二晚 60 人、每晚各 30 间用房。座位导出模型包含全部 150 人/150 座，但本轮没有渲染和检查 150 人 PNG 的可读性。

本样本 90 天快照正文约 10.9 MB（10.38 MiB），没有图片。此值不包含数据库索引/对象封装开销、回收站、成功回执、安全版本、长期手动版本、旧代次笔记及网络流量，不能视为单项目总占用或套餐结论。人数、备注长度、笔记篇数和正文长度增加都会扩大它。

## 负载证据的边界

- 90 次日结调用中，逻辑层读取笔记 1,080 次，写快照正文 90 次、历史索引 90 次、日结状态 90 次。单次日结需读取全部 12 篇笔记；CloudBase 实际请求/计费数量不能直接等同于这些方法调用计数。
- 列表返回每页 20 条元数据，但服务仍读取整个 historyIndex；本样本索引约 34 KB。长期手动版本和保留的日历摘要会继续增长，不能据此宣称已解决无限历史规模。
- 本机日结中位约 10.27 ms、P95 26.34 ms；恢复单次约 24.23 ms。MemoryStore 为事务回滚复制整个项目，且没有网络延迟，这些值仅记录本次 Node 25.8.1 运行，不是 CloudBase SLA 或手机性能。
- 尚需隔离云端的实际读写/事务耗时、数据库存储读回、任务失败重试和 90 天清理容量；真实手机/微信、独立客户端和实际下载仍按 TODO 验收。未据此冻结线上数量限制或建议升级套餐。
